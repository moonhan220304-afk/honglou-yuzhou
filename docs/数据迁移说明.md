# 历史内测数据迁移说明

## 一、结论先行

当前后端 `server/api-server.js` 启动时已做「列级幂等迁移」——用 `CREATE TABLE IF NOT EXISTS` + `PRAGMA table_info` 检查缺列再 `ALTER TABLE ADD COLUMN`。因此：

- **若旧库就是同一个 `hlm.db` 文件（同一套表结构、只是列更少）**：把旧文件放进 `DATA_DIR`（默认 `server/data/`），重启服务即可自动补齐新列，数据不丢，几乎零成本。
- **若旧库是另一套结构（不同表名/字段名，或旧版别的数据库）**：用 `scripts/migrate-legacy.js` 做导入。

## 二、迁移前必做

1. **备份**：脚本会自动 `copy` 目标库到 `hlm.db.bak-<时间戳>`；更稳的是在线一致性快照 `sqlite3 hlm.db "VACUUM INTO 'snapshot.db'"`。
2. **先验证密码哈希算法**（最易翻车点）：抽一个旧库用户，看 `pass_hash` 是哪种格式：
   - 新版 `scrypt`：`salt$hash`（salt 是 32 位 hex，hash 是 64 位 hex）。
   - 旧版若是 `bcrypt`（`$2a$...`）、`sha256` 或明文，导入后老用户**会登录不了**。
   - 处理：在 `server/api-server.js` 的 `verifyPassword()` 里按前缀识别算法，或提供「重置密码」通道。脚本会在报告里标出使用非 scrypt 哈希的用户。

## 三、迁移步骤（独立旧库 → 新库）

```bash
# 1. 停服（内测约 10 人，5–10 分钟足够）
systemctl stop honglou-api

# 2. 跑导入脚本（幂等，可重复跑）
node scripts/migrate-legacy.js /srv/legacy/hlm.db /srv/honglou-yuzhou-api/data/hlm.db

# 3. 看报告（before/after 计数 + 冲突/孤儿 + 密码提示）
cat /srv/honglou-yuzhou-api/data/hlm.db.migration-report.json

# 4. 校验后重启
systemctl start honglou-api
```

脚本特点：**幂等**（`INSERT OR IGNORE` + `migration_state` 表记录进度，重复跑结果一致）、**外键 id 映射**（旧 id → 新 id）、**冲突处理**（用户名撞名加 `_old` 后缀）、**时间戳自动换算**（毫秒/秒自动判定）、**孤儿行跳过并报告**。

## 四、回滚

SQLite 单文件，回滚就是换文件：

```bash
systemctl stop honglou-api
cp hlm.db.bak-<时间戳> hlm.db   # 用备份覆盖
systemctl start honglou-api
```

## 五、三个易翻车点清单

| 风险 | 现象 | 处理 |
|---|---|---|
| 密码哈希算法不兼容 | 老用户登录报「用户名或密码错误」 | verifyPassword 按前缀识别算法，或重置密码通道 |
| 时间戳单位（秒 vs 毫秒） | 时间显示为 1970 或未来年份 | 脚本自动判定（>1e12 为毫秒） |
| 用户名冲突 | 撞名用户导入失败 | 脚本加 `_old` 后缀并报告 |

## 六、对现有用户的影响

- 迁移 `sessions` 表则老用户登录态无感；不迁则需重新登录（建议一起迁）。
- 迁移期间 API 短暂不可用（停服窗口），前端静态站可继续打开。
